# Code cache

Code: `crates/mini_racer_engine/src/process/code_cache.rs`; `crates/mini_racer_engine/src/runner.rs` (`evaluate`, `compile`, `cache_uncached`, `recache`, `collect`); `crates/mini_racer_engine/src/process/fork.rs` (`Generation`, a forked child's copy). Tests: `crates/mini_racer_engine/tests/code_cache.rs`, `crates/mini_racer_engine/tests/code_cache_full.rs`, `crates/mini_racer_engine/tests/code_cache_first.rs`, `crates/mini_racer_engine/tests/code_cache_rebuilt.rs`. Overview: `ARCHITECTURE.md` "Code cache".

V8 accepts a code cache for any source of the same length and runs the code it holds, so `process::code_cache` finds an entry only by file name, startup snapshot, length and a digest keyed with the process's random `RandomState`; never key it by length or an unkeyed hash. An eval of 128 KiB or more is cached (`runner::CACHED_SOURCE`), up to 64 entries or 256 MiB; only one of a megabyte or more (`LARGE_SOURCE`) also reads its source from `process::sources` and has the memory it freed handed back, as sharing a smaller source would widen `behavior:shared-source-heap-stats@ruby`.

A sighting's sampled digest finds nothing: it decides only whether a script was seen before, so its cache is built at the second sighting, and whether a context keeping its own copy computes the full digest; a context sharing the source computes it from the first sighting (`Plan::Compile(Some(key))`). That context caches a first sighting of 16 MiB or more at once (`Plan::First`) when its top-level run took at least as long as its compile (`code_cache::worth_first`), as a bundle that renders as it loads does: a 44 MB server rendering bundle compiled in 186 ms and ran for 690, while 16 MiB of JSON compiled in 312 ms, ran for 55 and made a 24 MB cache. Such an entry never drops one a context has read (`Entry::read`); one that would is not kept, and its script is cached at its second sighting. `MINI_RACER_RS_CODE_CACHE_FIRST=always` or `never` (unstable, read once per process) decides in place of the timing, for tests.

The cache is built in `serve_one` after the dispatch, so it never counts against `timeout:`, and before the response, so a fork after the eval finds the runner idle; a `Building` claim makes contexts loading a script at once build it once and frees the key on any failure.

The context that stored an entry builds it once more, the same way, after its next call (a `Context#call` or an eval under 128 KiB: `runner::calls`, `recache`, `CodeCache::replace`), so the entry holds the functions that call compiled: later contexts' first Babel transform fell from 34 to 17 ms for 11 ms more on the builder's, and a 44 MB server rendering bundle's first render from 5.3 to 2.1 ms for 48 ms more. The entry built at the load stays for whatever loads before that call, as a pool's contexts or a forking master's children do; the rebuild claims nothing, keeps an entry gone since gone, and a first sighting's still unread drops no read entry either.

Until then the context holds the script's top level, which V8 would otherwise free, so every collection the runner asks for (`collect`: `low_memory_notification`, the one after `ensure_gc_after_idle:`, a heap limit's recovery) lets go of it first and the rebuild with it: a script whose top level declared 40,000 functions kept its heap 0.7 MB larger, and Babel's, MUI's and the 44 MB bundle's under 1 KB.
