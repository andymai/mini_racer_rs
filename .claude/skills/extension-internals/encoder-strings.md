# Strings the encoder sends

Code: `ext/mini_racer_rs/src/encode.rs` (`Encoder::string`, `MAX_DEPTH`); `ext/mini_racer_rs/src/rb_raw.rs` (`cached_ascii`); `crates/mini_racer_engine/src/text.rs` (`Transcoder`); `crates/mini_racer_engine/src/sys.rs` (`utf8_to_latin1`, `utf8_to_utf16`, through the simdutf V8 links); `crates/mini_racer_wire/src/write.rs` (`Writer::utf16_aligned`). Tests: `test/ruby/call_test.rb`, `test/ruby/nesting_test.rb`, `test/diff/corpus/argument-strings.json` (against mini_racer's strings and depths), `crates/mini_racer_engine/tests/transcoder.rs` (V8's reading of the decoded text against its reading of the UTF-8). Overview: `ARCHITECTURE.md` "Values".

The encoder writes a `Context#call`'s arguments without making `[name, *args]`, writes immediates before anything is pinned, and refuses a value nested past 512 levels as mini_racer refuses it (`MAX_DEPTH`).

mini_racer sends a String's bytes as UTF-8 unless its encoding is ISO-8859-1 or UTF-16LE, so every one of them that is all ASCII goes as one-byte text instead, the same characters, which V8 copies where it would scan for the first non-ASCII byte (`Encoder::string`). Whether it is ASCII comes from the coderange Ruby keeps in the String's flags (`rb_raw::cached_ascii`), else from its bytes, never from `rb_enc_str_coderange`: that scan checks each character of non-ASCII text, which made a call with an unscanned 1 MB non-ASCII String several times slower. Nothing writes the coderange back, so a String sent again is read again.

A coderange a C extension left stale after changing the bytes would be trusted, as Ruby itself trusts it, and so would one set without a scan: on Ruby 3.3, `rb_usascii_str_new` and `rb_usascii_str_new_cstr` mark their String 7-bit unread (3.4 and 4.0 mark only an empty one, and `rb_usascii_str_new_static` marks nothing), so non-ASCII bytes a C extension passes them go as Latin-1 where mini_racer sends them as UTF-8.

V8's deserializer decodes UTF-8 a byte at a time, twice, past its first non-ASCII byte, so a value's other text of 16 bytes up to 8 MiB (`text::LONG`) goes as what V8 would decode it to, decoded by simdutf (`Transcoder::decode`): one byte a character when each is at most U+00FF, else UTF-16 after the padding V8's serializer writes (`Writer::utf16_aligned`). Text simdutf finds invalid stays UTF-8, so its replacement characters are V8's own, and so does longer text: decoded, it takes a buffer of two bytes per byte and a request up to twice its length under the GVL, which would take a 100 MB String with one character past Latin-1 to about 500 MB at its peak, against 200 MB as UTF-8.

Keys and a call's name keep mini_racer's form, since the runner builds only calls whose keys are UTF-8 or ASCII; the runner's strings come out the same either way, since rusty_v8's `String::new_from_utf8` decodes UTF-8 through simdutf as well. So the gain is in calls V8 reads whole; in a call the runner builds, the decoding only moves into the encoder, under the GVL, and a long Latin-1 value alone measured a little slower there.
